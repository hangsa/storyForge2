## 一、目标与非目标

### 1.1 Goal

修一个编排层缺陷:手动模式下,通过 `POST /api/stage4/write-scene` 写入场景成功,但状态机从不把章节从 `in_progress` 推进到 `completed`,因为 `in_progress → completed` 的转移只发生在 `_advance_chapter()` 内 (`stage4_writing.py:702`),而该函数只有两条调用路径:
- autopilot 执行器的 `archival` 队列项 (`stage4_async_executor.py:139`)
- 显式的 `POST /api/stage4/advance-chapter` HTTP 端点

手动模式下两条都不走,因此章节会一直卡在 `in_progress`。前端目前没有 UI 暴露 advance-chapter,所以用户无法触发修复。

修复策略:不引入自动触发(保持 v1.10 的最小变更面),而是把 **ChapterTreePanel 的 刷新 按钮**绑到一个轻量级的、幂等的"修复 stuck 章节"操作。刷新时,如果发现某章节的所有场景都已收尾但状态仍为 `in_progress`,就把它推进到 `completed`。不动 LLM、不动 L2、不动 checkpoint —— 纯状态机修复。

### 1.2 Non-goals (本次修复)

- **不**改 `_write_scene_chapter()` 行为(保持纯函数语义,autopilot 路径不受影响)
- **不**改 `_advance_chapter()` 行为(其 `fake=True` 参数已经存在,本次不暴露)
- **不**自动触发 advance(用户点击 刷新 才触发,符合用户期望"可以不是自动更新")
- **不**改 progress.json 字段或写入路径
- **不**改 autopilot 路径(它走 queue-based 编排,本来就工作正常)
- **不**在 UI 里加新的"推进章节"按钮 —— 复用现有 刷新 按钮即可
- **不**调用 SummaryArchiver LLM / 不重建 L2 摘要 / 不写 checkpoint —— stuck 章节是历史数据,LLM 修复成本高且会覆盖可能的手动编辑

## 二、根因复述

`progress.json` 章节状态机:

```
pending → in_progress → completed   ← 正常路径
                       → force_passed / skipped (Scene 维度)
```

`_advance_chapter()` (`stage4_writing.py:603-734`) 是唯一把章节从 `in_progress → completed` 的地方:
- `ch_progress["status"] = "completed"` 在 line 702
- `progress["current_chapter"] = current_chapter + 1` 在 line 704
- 该函数被两条路径调用:
  - `stage4_async_executor.py:139` (`AsyncStage4Executor._archival`)
  - `stage4_router.post("/advance-chapter")` 在 `stage4_writing.py:925-934`

`POST /api/stage4/write-scene` (`stage4_writing.py:737-754`) 调用 `_write_scene_chapter()`,该函数:
- 写入单个场景的 draft.md 和 meta.json
- 更新 progress.json 的 `chapters[i].scenes[]` 把该场景标记为 `completed`/`force_passed`
- 但**不**检查章节是否全部完成,**不**触发 advance

因此手动模式下,场景写完后章节永远停在 `in_progress`。

`proj_cc4ca4ae` 案例验证:

```bash
$ python3 -c "import json; p=json.load(open('projects/proj_cc4ca4ae/progress.json')); ch=next(c for c in p['chapters'] if c['chapter_number']==13); print(ch['status'], [s['status'] for s in ch['scenes']])"
in_progress ['force_passed', 'completed', 'completed', 'force_passed']
```

`current_chapter=13`,ch13 所有 4 个场景都已收尾,但章节状态卡住。

## 三、新增 REST 端点

```
POST /stage4/repair-progress
Body: { project_id: string }
→
{
  "error": false,
  "code": "OK",
  "message": "已修复 N 个章节",
  "detail": {
    "repaired_chapters": [13, 12],   // 按 chapter_number 升序
    "current_chapter": 14             // 新值;若无需推进则与旧值相同
  }
}
```

**实现位置:** `backend/api/stage4_writing.py`,作为 `stage4_router` 的新 handler。注册走现有的 `router.include_router(stage4_router)` 链(无需改 main.py)。

**算法(伪代码):**

```python
@stage4_router.post("/repair-progress")
async def repair_progress(data: dict) -> dict:
    project_id = data.get("project_id", "")
    if not project_id:
        raise HTTPException(400, {"error": True, "code": "VALIDATION_ERROR",
                                  "message": "project_id 不能为空", "detail": {}})

    project_dir = fm.projects_dir / project_id
    if not project_dir.exists():
        raise HTTPException(404, {"error": True, "code": "PROJECT_NOT_FOUND",
                                  "message": f"项目 {project_id} 不存在", "detail": {}})

    progress = fm.read_json(project_id, "progress.json")
    if progress is None:
        # 全新项目,无可修复内容,静默返回空集
        return {"error": False, "code": "OK", "message": "",
                "detail": {"repaired_chapters": [], "current_chapter": 1}}

    outline = fm.read_json(project_id, "outline.json") or {}
    outline_chs = {c.get("chapter_number"): c for c in outline.get("chapters", [])}

    DONE_STATUSES = {"completed", "force_passed", "skipped"}
    repaired: list[int] = []
    for ch_progress in progress.get("chapters", []):
        if ch_progress.get("status") != "in_progress":
            continue
        ch_num = ch_progress.get("chapter_number")
        outline_ch = outline_chs.get(ch_num)
        if outline_ch is None:
            # 无 outline 真值,不修复(防御性,避免凭空发明完成状态)
            continue
        planned = outline_ch.get("scene_plan", [])
        if not planned:
            continue  # 无场景大纲,跳过
        progress_by_num = {s.get("scene_number"): s.get("status")
                           for s in ch_progress.get("scenes", [])}
        all_done = all(progress_by_num.get(s.get("scene_number")) in DONE_STATUSES
                       for s in planned)
        if all_done:
            ch_progress["status"] = "completed"
            repaired.append(ch_num)

    if repaired:
        # current_chapter 仅向前推进,不回退
        new_current = max(progress.get("current_chapter", 1),
                          max(repaired) + 1)
        if new_current != progress.get("current_chapter", 1):
            progress["current_chapter"] = new_current
        fm.write_json(project_id, "progress.json", progress)

    return {"error": False, "code": "OK",
            "message": f"已修复 {len(repaired)} 个章节",
            "detail": {"repaired_chapters": sorted(repaired),
                       "current_chapter": progress.get("current_chapter", 1)}}
```

**关键不变量:**

1. **无 LLM**: 不调用 SummaryArchiver、不触发 ReaderOS 快照、不写 checkpoint。这些对"修复历史卡住的章节"是过度的 —— 章节早就写完了,内存应该是 stale 但用户已经接受了的。
2. **幂等**: 第二次调用同样的状态返回 `{repaired_chapters: [], current_chapter: <unchanged>}`。每次都重写 progress.json 一次但内容相同(可接受的成本,文件很小)。
3. **current_chapter 单调**: 永不复退。即使 ch12 卡住、current_chapter=15,修复 ch12 不会把 current_chapter 拉回 13。
4. **顺序**: 按 chapter_number 升序输出,便于前端展示和测试断言。
5. **无外溢**: 不创建 `progress.json["chapters"]` 中不存在的章节占位符,不影响 `next_ch` 的 append 逻辑(那仍然是 `_advance_chapter` 的职责)。

## 四、前端接入

### 4.1 新增 API 方法

`frontend/src/api/client.ts`,镜像现有 `advanceChapter` 的写法:

```ts
repairProgress: (projectId: string) =>
  request<{
    repaired_chapters: number[];
    current_chapter: number;
  }>(
    "POST",
    "/stage4/repair-progress",
    { project_id: projectId },
  ),
```

### 4.2 绑定 刷新 按钮

`frontend/src/pages/WorkspacePage.tsx`,目前传给 `ChapterTreePanel` 的是:

```tsx
onRefresh={() => setReloadKey((k) => k + 1)}
```

新 handler:

```tsx
onRefresh={async () => {
  if (!projectId) return;
  try {
    const r = await api.repairProgress(projectId);
    if (r.repaired_chapters.length > 0) {
      show(`已推进 ${r.repaired_chapters.length} 个章节`);
    }
  } catch (e) {
    const msg = e instanceof Error ? e.message : String(e);
    show(`章节收尾失败：${msg}`);
  }
  setReloadKey((k) => k + 1);  // 无论 repair 成功失败,UI 都重新拉取真实磁盘状态
}}
```

设计要点:
- `setReloadKey++` **无条件**触发 —— repair 失败时 UI 仍能反映磁盘当前真实状态
- 成功且有修复 → 短 toast("已推进 N 个章节")
- 成功但无修复 → 静默(健康项目无需打扰用户)
- 失败 → 错误 toast,但仍 reload,符合"诚实空状态"原则
- 不阻塞其它 UI —— `api.repairProgress` 是一次 HTTP 调用,本身是 IO-bound 但磁盘操作很快

### 4.3 ChapterTreePanel 不需要改动

`onRefresh` prop 已经是 `() => void`。新的 handler 签名是 `async () => void`,但调用方不 await,且 `onRefresh` 的类型签名兼容(`() => void` 接受任何返回值的函数)。**组件 API 不动,纯外层 wiring 改动**。

## 五、错误处理

| 场景 | 行为 |
|---|---|
| 后端:`project_id` 为空 | 400 `VALIDATION_ERROR`(envelope 格式) |
| 后端:项目目录不存在 | 404 `PROJECT_NOT_FOUND`,与 `list_scene_drafts` (`stage4_writing.py:175-180`) 对齐 |
| 后端:`progress.json` 缺失 | 返回 `{repaired_chapters: [], current_chapter: 1}`,与 `get_progress` 在 progress 缺失时的宽松行为 (`stage4_writing.py:890-904`) 对齐 |
| 后端:`outline.json` 缺失 | 所有 in_progress 章节因"无 outline 真值"全部跳过,返回空集 |
| 后端:章节在 outline 不存在 | 跳过该章节,防御性(避免凭空发明完成状态) |
| 后端:outline 场景数 ≠ progress 场景数 | 仅当 **每个** outline 场景都在 progress.scenes 中有终态条目时修复 —— outline 缩容(mid-run 编辑)会导致该章不修复,这是更安全的选择 |
| 后端:`progress.json` 写入失败 | 500(Python 抛异常,FastAPI 默认处理) |
| 前端:`repairProgress` 网络错误 | Toast 错误信息;`setReloadKey++` 仍触发,UI 仍刷新 |
| 前端:用户点击 刷新 但项目健康 | repair 返回空列表 → 静默,UI 照常刷新 |
| 多章节卡住 (ch12 + ch13 都卡,current_chapter=13) | 一次调用全部修复;current_chapter 推进到 `max(13, 13+1) = 14` |
| current_chapter 已经领先于 stuck 章节 (ch12 卡、current_chapter=15) | ch12 修复,current_chapter 保持 15(单调,不回退) |
| 多次点击 刷新 | 幂等:第二次返回空集,UI 不变 |

### 8.5 Ambiguity scan

- "修复后是否重建 L2 摘要?" → 显式不重建 (1.2 节)。理由:stuck 章节场景已经写完很久,L2 stale 是已发生的事,重建要花 LLM tokens 且可能覆盖用户后续的手动编辑。

- "outline 编辑缩容后部分场景没了,如何处理?" → 不修复 (3 节算法 outline 校验)。理由:保守策略,告诉用户"这章不完整"比"假装它完整"更安全。
